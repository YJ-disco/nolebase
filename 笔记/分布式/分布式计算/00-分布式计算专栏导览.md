# 分布式计算专栏导览

本专栏收录**"把计算摊到多台机器上"这条线上的编程模型与运行时**：批处理与内存计算、图计算、交互式分析、以及流处理各自是怎么定义数据共享与容错边界的。

它和相邻专栏的分工是**层次**而不是技术栈：

| 不收 | 去哪看 | 本专栏只关心 |
| --- | --- | --- |
| 存储系统自身的内部实现（GFS、Bigtable、Dynamo…） | [[00-分布式存储专栏导览\|分布式存储]] | 计算层把什么当作"稳定存储"、复用它时付什么代价 |
| 共识算法本身（Paxos、Raft、Zab） | [[00-一致性共识算法专栏导览\|一致性共识算法]] | 计算框架的容错走的是共识，还是能靠别的性质绕开 |
| 集群调度与运维（Chubby、Borg、Dapper） | [[00-集群与运维专栏导览\|集群与运维]] | 计算任务被交给谁去放（Borg 那一层） |

换个说法：存储专栏讲"数据放哪"，共识专栏讲"节点怎么达成一致"，本专栏讲**"计算怎么被组织成可并行、可恢复的形状"**。

## 目录

- 01 · [[01-RDD|RDD]] —— 用**粗粒度变换换容错**：把容错寄托在**血统（lineage）**而不是复制上，从而绕开对可变状态做细粒度更新时的两种昂贵选项（跨机复制、跨机记更新日志）。**narrow 与 wide 依赖**的区分（分区按序关系定义，而非按算子名）决定两件事：能否单机流水线、以及单点故障会不会牵连 RDD 的所有祖先；**RDD 级 LRU 逐出**与"同一 RDD 的新旧分区不互相逐出"这条反直觉规则；**checkpoint 的判据**（血统长且含 wide 依赖才值得，对稳定存储做 narrow 依赖的可能永远不值得）；只用 **14,000 行 Scala** 跑在 Mesos 上、绝大多数算子 **<20 行**；以及把 20 倍加速拆成三条可量化的开销来源（Hadoop 栈至少 25 秒的最小开销、HDFS 每块 2 秒、反序列化 7+3 秒）；**血统图不到 10 KB 对 100 GB 工作集**这个对照
- 02 · [[02-Pregel|Pregel]] —— **顶点中心 + 超步（BSP）**这条路线：`Compute()` 只描述"顶点 $V$ 在超步 $S$"的行为，且只暴露 $S-1 \to S \to S+1$ 的通信，于是**天然没有死锁与数据竞争**。**投票停机**的三条规则（超步 0 全 active、停用后被消息唤醒需显式再停、整体终止 = 全 inactive 且无消息在途）；**为什么拒绝远程读**（延迟无法隐藏，消息可以批量摊薄）；**Combiner 默认关闭**的理由（不存在机械办法找与 `Compute()` 语义一致的合并函数）与 SSSP 上**消息流量降到四分之一以下**；**Aggregator** 的 sticky 语义与"用树形归约而非 worker 链以并行用 CPU"；**拓扑变更的偏序**（先删后增、删时先边后点、所有变更在 `Compute()` 之前）与**纯局部变更立即生效**；**分区只由顶点 ID 决定**（顶点不存在也能算出归属）与"顶点到 worker 的分配是唯一不透明处"；**worker 里 active 标志与消息队列各存两份**的原因（并发收消息 + 只收上一超步的消息）；**受限恢复**要求算法确定性；十亿顶点 / 1270 亿边上的三组实测数字与"这些不是最好成绩"的声明
- 03 · [[03-Dremel|Dremel]] —— **只读嵌套数据的交互式分析**，走的是与 RDD/Pregel 正交的另一条路：不迭代，而是把**列裁剪**做到底。**repetition level 与 definition level** 这套编码是核心 —— 光有值不足以表达结构，前者记录"在路径上哪个重复字段处发生了重复"（`0` 表示新记录开始），后者记录"路径上本来可能未定义的字段里实际出现了几个"，**用整数而非 is-null 位是为了让叶子字段带着父字段的出现信息**；NULL 不显式存、levels 按需要的位数打包；**记录装配是一台有限状态机**，状态 = 各被选字段的 reader、转移用 repetition level 打标签，**取字段子集时构造更简单的 FSM**；serving tree 的**每层查询重写**（`COUNT` 改写成 `SUM` 包一层）与"**多分组的聚合才吃这一层**"；**把读得更少这件事量化成三级台阶**（MR on records 87 TB → MR on columns / Dremel 0.5 TB，小时 → 分钟 → 秒）；以及"**记录装配与解析各自都能让执行时间翻倍**"这条把 Dremel 与 MapReduce 都框住的结论
- 04 · [[04-Parameter Server|参数服务器]] —— **把"共享参数"这件事系统化**：worker 分担数据与计算，server 组维护全局参数的一个分区。整套设计压在**一条前提**上 —— **机器学习算法对扰动容忍，于是一批本来很难满足的系统约束可以被放松**。**三层压缩**：`range push/pull` 把"一个小值的逐条 KV 更新"变成**按区间批量通信**（根因是"值太小、每条更新一次 KV 操作开销太高"）；**区间向量时钟**把朴素 $O(nm)$ 的空间压到 $O(mk)$（依据是"按区间通信让许多参数共享同一时间戳"）；**键缓存 + 只发非零值**的两处消息压缩。**聚合后再复制**把复制的带宽放大从 $k$ 倍压到 $k/n$。**三种一致性模型**（Sequential / Eventual / Bounded delay，$\sigma=0$ 即顺序、$\sigma=\infty$ 即最终）都靠**任务依赖图**实现，并把权衡交给算法设计者；实测给出 $\sigma$ 的最优点。还有一处态度上的差异：它**可以选择不替换失败的 worker、甚至主动终止最慢的 worker**，因为丢一点训练数据对模型影响很小
- 05 · [[05-S4|S4]] —— **流计算的最早形态之一**，也是全栏里唯一把「**为什么不能拿批处理平台改造**」讲透的一篇：MapReduce **在静态数据上调度批作业**，而流的范式是**事件以我们无法控制的速率流入** —— 系统**要么跟上速率、要么淘汰事件**（load shedding）；对「定长分段 + MapReduce」的批评也在这里（**延迟与段长成正比**，段小则开销与跨段依赖上升，段大则延迟上升，**最优段长依应用而定**）。三个抽象要分清：**PE 的身份四要素**（功能 / 事件类型 / 被键属性 / 该属性的取值）、**无键 PE 用在输入层赋键**、**PE prototype 由 PN 在遇到新取值时克隆一次** —— 由此得到"同键事件保证落在同一个 PN"这条去中心的前提。它还**公开写明两条假设**：**有损故障切换可接受**（PE 状态在本地内存、交接即丢，靠输入流重生成）与**运行中的集群不加不减节点**，并在实测里现身（CTR 场景下 PN 故障就退回到长期估计）。实测给出**约 10 Mbps 处开始劣化**这条曲线与在线 CTR 提升 3% 的结果
- 06 · [[06-Storm|Storm@Twitter]] —— 本栏的收尾，也是**唯一一篇把生产运维当主体**的：**Nimbus / Supervisor / worker / executor / task 五层**的职责边界与 **fail-fast + 无状态**这条韧性来源；**at-least-once 的 acker 机制**用**按位 XOR 校验和**把"溯源树"的内存占用压掉（且能成立是因为**通信走 TCP/IP、不会重复投递**）；**五种分组策略**对应并行数据库的 exchange 算子。三个运维故事最值得读：**ZooKeeper 被打爆的四代配置演进** —— 从共享集群到专用硬件、到 300 worker 撞墙、到约 1200 worker，最后**解析 tcpdump 发现 67% 的写来自 `KafkaSpout` 的 offset 上报、33% 里 96% 来自每 3 秒一次的心跳**，于是第四代改成**改代码而不加硬件**；**开销对照实验**（同一份逻辑，不用 Storm 单机 300K msgs/sec / 用 Storm 关可靠性 660% CPU / 开可靠性要 3 台机、924%）**把可靠性机制的代价量到了反序列化的 3 倍**；以及 **max spout pending 的自动调参状态机**。最后是**抽掉机器**的韧性实测：16 台降到 4 台，吞吐 6.8M → 2.2M tuples/分、延迟 7.8 ms → 45 ms，每次移除都出现尖峰但很快稳定

## 阅读顺序

**01 → 02 → 03 → 04 → 05 → 06**，按**数据形态**递进：

- **RDD** 立起"内存计算 + 血统"这个地基，后面几篇的容错讨论都回到它；
- **Pregel** 是 RDD 明确声称能表达的一个模型，两篇构成一组正面对照：Pregel 是**专用化**的极致（顶点中心 API + 超步同步 + 只为图优化），RDD 声称能用 200 行库把它表达出来。并读能看清"专用框架"与"通用抽象"的边界落在哪；
- **Dremel** 走另一条路：不迭代，而是把**嵌套结构的列式表示**与树形聚合做出来；
- **Parameter Server** 把"参数"当作被分片的共享状态，是机器学习训练侧的取舍；
- **S4 与 Storm** 是流处理的早期形态与工程化版本，两篇构成一组演进对照。
