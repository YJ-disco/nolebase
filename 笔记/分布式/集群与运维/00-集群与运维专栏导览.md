# 集群与运维专栏导览

本专栏收录**把一堆机器当成一台机器用的那三件基础设施**：**协调服务**（Chubby）、**集群调度**（Borg）、**链路追踪**（Dapper）。

它们与相邻专栏的边界是**关注点而不是技术栈**：

| 不收 | 去哪看 | 本专栏只关心 |
| --- | --- | --- |
| 存储系统自身的内部实现（GFS、Bigtable、Dynamo、Spanner…） | [[00-分布式存储专栏导览\|分布式存储]] | 它们**作为被调度、被协调、被观测的对象**那一面 |
| 共识算法本身（FLP、Paxos、Raft、Zab） | [[00-一致性共识算法专栏导览\|一致性共识算法]] | Chubby 只讲**建在 Paxos 之上的锁服务接口**，以及它为什么不做成一个 Paxos 库 |
| 分布式计算模型（Pregel、RDD、参数服务器） | `分布式计算/`（待建） | Borg 只负责**把这些计算任务摆到机器上** |

换个说法：存储与共识专栏回答"数据怎么放、节点怎么达成一致"，本专栏回答"**任务放哪、谁来发现彼此、出了问题怎么看见**"。

## 目录

- 01 · [[01-Chubby|Chubby]] —— 一个**锁服务**而不是 Paxos 库的四条论证（开发者不按高可用规划、服务需要"公告结果"的位置、锁接口更熟悉、锁服务把"推进所需的最少活节点数"压到 1）；**粗粒度与细粒度的完整取舍对照**（持有时长、对锁服务的负载、锁服务短时不可用、锁迁移代价）；cell 的 5 副本与 **master lease**；类 UNIX 命名空间与**四个单调递增 64 位数**（instance / content generation / lock generation / ACL generation）；handle 的 check digits 与 UNIX fd 的对照；**advisory 锁**与只给用到锁的交互引入序号的 **sequencer**，以及给不支持 sequencer 的服务器兜底的 **lock-delay（上限一分钟）**；六个事件（含两个被回头否掉的）与**只失效不更新**的缓存协议；**会话租约、KeepAlive 搭车回传事件与失效、jeopardy 与 grace period**；**master fail-over 的九步重建**与 client epoch；线上快照（**KeepAlive 占 RPC 93%、共享锁 0**、RPC 1–2k/s、文件 0–1 KB 占 90%）；四类经验教训（含 **TCP 退避策略迫使 KeepAlive 改用 UDP**）
- 02 · [[02-Borg|Borg]] —— 三条收益与**中位 cell 约 1 万台机器 / 一个忙碌 Borgmaster 10–14 核 + 50 GiB** 的规模锚点；**prod 与非 prod 同机混跑**（98% 的机器），分离要多 20–30% 机器，以及用 **CPI 量化干扰**的三组数字（加一个 task 使他人 CPI +0.3%、共享 cell 比专用差约 3%）；**job / task / alloc 三层抽象**与 `SIGTERM` 只送到约 80% 的现实；**priority 带、production 带内禁止互抢、quota 属于准入控制而非调度**；Borgmaster **五副本 + Paxos + Chubby 锁**、checkpoint 与 **Fauxmaster** 模拟器；调度两段（**feasibility 用"可用"资源含可驱逐部分、scoring 的四条内建判据**）、**E-PVM 的 "worst fit" 与 "best fit" 的取舍**、启动延迟中位 25 秒且 **80% 花在 package 安装**；扩展三招（**score caching / equivalence classes / relaxed randomization**）与"几百秒 vs 禁用后超 3 天"的对照；**Borglet 与 link shard 的分工**（Borglet 报全量、link shard 只报差分）；99.99% 可用性的三条来源与**"每 cell 独立"才是反对大 cell 的主因**；**cell compaction** 评估方法；**资源回收的三条 reservation 演化规则**与三档参数实验；**chroot + cgroup + appclass + 可压缩/不可压缩**的隔离体系；三慎（job 作唯一分组、一机一 IP、为 power user 优化）四取（alloc、集群管理不只是任务管理、自省、master 是内核）与 Kubernetes 的逐条对应
- 03 · [[03-Dapper|Dapper]] —— 两个前提要求（**无处不在的部署、持续开启**）与三个设计目标（**低开销、应用级透明、可伸缩**），以及"把埋点限制在一小撮公共库"这条达成透明的手段；**trace tree / span / annotation** 数据模型与**双主机 span 是最常见一类**带来的时钟偏斜处理；**三个埋点位置**（线程局部存储、公共控制流库、RPC 框架）；**两级采样**（运行时按"期望每秒采样 trace 数"自适应 + 收集期**按 trace id 哈希整条取舍**）与生产集群**每天超 1 TB** 的产数据量；三段收集管线、**中位不到 15 秒**的延迟与 98 分位的双峰；**out-of-band 的两个理由**（带内会淹没应用数据、假设 RPC 完美嵌套）；只存方法名不存载荷与两类意外安全收益；**40 + 33 个应用需要手工传播**、**C++ 不到 1000 行 / Java 不到 800 行**的运行时库；**三组开销量化**（root span 204 ns / 非 root 176 ns / annotation 9 与 40 ns；daemon 不超单核 0.3%；每 span 426 字节、占网络流量 <0.01%；采样 1/1 时延迟 +16%、1/16 以下落在误差内）；**DAPI 三种访问与"索引只比数据省 26%"**；UI 五步工作流与**典型工作日约 200 人**；六类用例（含 **Ads Review 延迟改善约两个数量级**、长尾延迟的三条发现、网络仪表盘**不到两周建成**）与六条局限

## 阅读顺序

**01 → 02 → 03** 按**时间与依赖层次**排：

- **01 Chubby（OSDI 2006）** 是最底层的协调原语 —— 它提供的是"锁 + 小文件"这种别的系统可以直接搭上去的接口；
- **02 Borg（EuroSys 2015）** 是建在它上面的调度层 —— **Borgmaster 选出后取一把 Chubby 锁**，task 的 BNS 名字也写进 Chubby 文件；
- **03 Dapper** 是横切在两者之上的观测层，既追踪 Borg 跑起来的服务，也被 Borg 的容器与 daemon 分发机制托着。

先读 01 再读 02，是因为 02 里那句"取一把 Chubby 锁好让其他系统能找到它"只有在知道 Chubby 给了什么之后才读得出分量。

## 三组对照

- **Chubby ↔ Borg** —— 一个"锁服务被当成选主与命名底座"的完整实例。与 [[02-Bigtable|Bigtable]] 对 Chubby 的五处依赖并读，能看清 Chubby 在整个 Google 栈里到底被用来做什么：**选主、发现、存引导位置、存 schema、存 ACL**。
- **Borg ↔ Dapper** —— 同一批机器的两个视角。**Borg 回答"任务放在哪、活了没"，Dapper 回答"一次请求分别在各层花了多少时间"。** 一篇是控制面，一篇是观测面；Borg 的容器与 daemon 机制正是 Dapper 能铺满每台机器的前提。
- **Chubby ↔ Dapper** —— **分层存储链**在两个方向上都出现：App Engine → 实体存储系统 → Bigtable → Chubby 与 GFS。Dapper 用它说明"**分层系统难以做应用层归因**"（同一个 Bigtable cell 的 GFS 流量来自几个用户，在 GFS 层看不出来），Chubby 用它说明自己的客户端里有多少是"把 Chubby 当成自己分布式数据结构的根"。
