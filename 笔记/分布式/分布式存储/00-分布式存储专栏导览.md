# 分布式存储专栏导览

本专栏收录**分布式存储系统的具体实现** —— 文件系统、宽表、KV、关系型数据库、对象存储各自是怎么把前几个专栏里的理论（一致性模型、共识、分区）落成一套可运行系统的。

排序原则是**按依赖关系**：Google 系的 GFS → Bigtable → Spanner 是一条堆叠关系（上层建在下层之上），读的时候顺着这条链走最省力；其余系统可以按需挑。

## 目录

- 02 · [[02-Bigtable|Bigtable]] —— 三维有序 map 的数据模型、SSTable 与 **Chubby 的五处依赖**（含不可用率的实测）、commit log + memtable + SSTable 的三层状态、**三档 compaction 对"已删数据"的不同处理**、locality group / 两遍压缩（10:1）/ 两级缓存 / Bloom filter / **commit log 合流后的排序恢复**
- 03 · [[03-Dynamo|Dynamo]] —— 四条设计考量与 **99.9 分位 SLA**（为什么均值/中位数不够）、**虚拟节点**、**向量时钟与 D1–D5 的完整演化**、$(N,R,W)$ 与延迟由最慢副本决定、**sloppy quorum + hinted handoff**、**Merkle 树反熵**、**三种分区策略的复盘**（Strategy 1 的根因是"分区与放置被缠在一起"）、生产配置 $(3,2,2)$
- 04 · [[04-Spanner 与 F1|Spanner 与 F1]] —— **TrueTime 的 TTinterval 与它的 GPS+原子钟实现**（$\epsilon$ 的锯齿与实测）、**外部一致性的两条规则与四步不等式证明**、commit wait 的 $2\epsilon$ 代价、**safe time**、读写事务的客户端驱动 2PC 与快照事务的 scope 推断；F1 从手工分片 MySQL 迁过来的定位
- 05 · [[05-Cassandra|Cassandra]] —— Dynamo 的分布式方案 + Bigtable 的数据模型；**为什么用保序哈希**、负载均衡**不用虚拟节点而是移 token**（可控且确定）、三档复制策略、用 ZooKeeper 存范围元数据、**Accrual Failure Detector 与 $\phi$ 的刻度表**、bootstrap 为什么必须显式触发、本地持久化的全套参数（专用 commit log 盘 / Bloom filter / 256K 列索引）
- 06 · [[06-Aurora|Aurora]] —— **为什么 2/3 法定人数不够**（AZ 故障是**相关故障**，会叠加 AZ 间的背景噪声故障）→ **6 份 / 3 AZ / 4 写 3 读**的推导；**降 MTTR 而不是降 MTTF** 与 10 GB 分段 + PG；**日志即数据库**（后台物化只是缓存、粒度从全局链改成单页链）；存储节点八步与**负相关调度**；LSN + gossip 替代 2PC；实测（事务 35 倍、db 侧 I/O 少 7.7 倍、存储层少 46 倍）
- 07 · [[07-HBase 与 LSM-Tree|HBase 与 LSM-Tree]] —— **LSM-Tree 的完整代价模型**：四个成本参数与 $\text{COST}_p/\text{COST}_P \approx 1/10$、插入成本公式 $2\text{COST}_p/M$ 与 $K_1 \approx 0.67$、**"$M < K_1 \cdot \text{COST}_p/\text{COST}_P$ 就该改回 B 树"这条判据**、最优 $C_0$ 的操作性推导、定理 3.1（**所有 $r_i$ 相等**）、温度模型 $T_f$/$T_b$ 与 1995 年成本数字；HBase 的 HMaster / region server / ZooKeeper 三段式与四个存储组件
- 08 · [[08-MegaStore|MegaStore]] —— 在 Bigtable 上补跨行事务：**entity group** 的定义与三个真实划法（Email / Blogs / Maps）、"跨组异步消息**只用在逻辑距离上、数据中心之间全是同步复制**"这条澄清、**Pre-joining with keys** 用键序代替 join、local/global 索引与 `STORING`/`Repeated`/`Inline`、**把元数据与事务日志塞进单个 Bigtable 行**这个关键技巧、成本透明的 API 哲学与 merge join 的替代方案
- 09 · [[09-Windows Azure Storage|Windows Azure Storage]] —— 三层分工（**流层管"写下的不会变"、分区层管"谁最新与写入顺序"、FE 无状态**）、stream / extent / block / seal 与 **Stream Manager 的三条"不做"**、**为什么这里不需要 lease**（extent 只追加、primary 固定）、multi-block append 的契约与重复记录处理、**流层给分区层的两条保证全是不可变性**、Object Table 与 RangePartition、**加 journaling 反而把 append 延迟从 30 ms 降到 6 ms**
- 10 · [[10-Haystack|Haystack]] —— 全篇在做减法：**唯一要解决的是"一次读取花几次磁盘 I/O"**；NAS 阶段的问题链（每目录几千文件→**单图 >10 次**；降到几百→**稳定 3 次**；file handle 缓存与 `open by filehandle` **收效很小**）与 **CDN 不能替代后端的长尾请求**；needle 字段与 **(key, alternate key) 编码 4 种尺寸**、**cookie 抵御枚举**、**禁止覆盖 + 用 offset 定最新版本**、index file 的 **orphan 与陈旧 record**；**10 字节/照片、40 字节/图 对 536 字节 xfs inode**；1 GB extent / 256 KB stripe、pitchfork、28% 成本与 4 倍读速率
- 11 · [[11-Ceph|Ceph]] —— 全篇与前面所有"查表找数据"的方案相反：**消除文件分配表、用生成函数替代**（作者称其为设计中的"简化力量"）；三个设计特征（**解耦数据与元数据 / 动态子树分区 / 把复制·迁移·故障检测·恢复下推给 OSD**）；file → object → PG → OSD 的**三层寻址**与 **~100 PG/OSD**；**CRUSH 一次解决"该存哪"与"存哪了"**、cluster map 的四层结构与 placement rules、$O(\log n)$ 与几十微秒；**ack 与 commit 分离**、**down 而不 out** 避免系统性故障触发大范围重复制、PG 版本 + 变更日志的并行恢复；**80 字节 inode 对 xfs 的 536 字节**；EBOFS 的 extent + B-tree；128 MDS 的 **25 万 ops/sec**
- 12 · [[12-Tango|Tango]] —— 唯一一篇不解决"数据怎么摆"、只解决"抽象怎么给"的：**共享日志就是对象本身，view 只是软状态**；元数据服务的三条既有路线与**多系统拼装**的代价（ZooKeeper + BookKeeper + 自研协议）；CORFU 四调用 / write-once 地址空间 / **sequencer 为什么不是单点故障**（只存一个 64 位整数、且"找 tail"只是优化）与三代性能（200K → 570K → 2M）；**四个性质的逐条推导**（一致性靠 check、持久性靠重放、**offset 当索引**、弹性靠加 view）；OCC 提交记录与 **read set 版本**、**对象代码零修改**、细粒度版本；**分层分区与 stream**（`readnext` / `multiappend` / 与 sharding 的交换）；**decision record** 与四种远端情况；stream header 的 **$K=4$ 与 12 字节**；评测（135K 读/秒、180K 读/秒、200K 事务/秒）与 **TangoZK 不到 1000 行对原版 13K 行**

## 阅读顺序


**01 → 02 → 04**（GFS → Bigtable → Spanner）是 Google 存储三代的主链，层层堆叠，建议连读。

其余各篇可以按兴趣挑，但有两组对照值得放在一起看：

- **03 Dynamo → 05 Cassandra**：同一条"去中心 + 最终一致"的路线，Cassandra 在数据模型上换了 Bigtable 那套；
- **04 Spanner 与 06 Aurora**：两种把"跨地域强一致"做出来的不同路径 —— 一个靠**全局时钟（TrueTime）**，一个靠**共享存储层 + 法定人数**。
- **12 Tango 与 04 Spanner / 02 Paxos**：三种"跨分片强一致"的定序来源 —— **全局物理时钟（TrueTime）/ 共识协议 / 一条共享日志**；Tango 的卖点是**绕开共识协议**，但底层 CORFU 的 chain replication + sequencer 并没有真的省掉定序
- **10 Haystack 与 11 Ceph**：同一件事（"数据在哪"）的两条相反路线 —— Haystack **把元数据整体压进内存去查**，Ceph **把位置整个算出来、连表都不建**；
- **01 GFS / 07 HBase 与 LSM-Tree / 10 Haystack**：同属"**追加 + 后台合并**"这一族的三个不同落点 —— GFS 的落点是 chunk 与批量负载，LSM-Tree/HBase 的落点是多层 rolling merge 与代价模型，Haystack 的落点是**为了读吞吐把元数据整体搬进内存、并消掉文件系统元数据那几次 I/O**。
